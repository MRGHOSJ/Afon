# Project structure

This page tours the files Afon reads and writes, both in your project
folder and inside the cluster.

## Your project folder

A typical flow project:

```
my-app/
├── flow.yaml            # the flow (required name; -f points at it)
├── deploy/              # your Kubernetes YAML (referenced by k8s-manifests)
│   ├── deployment.yaml
│   └── service.yaml
├── generated.yaml       # created by `afon render` (gitignored)
└── .afon/               # local state (gitignored)
    ├── cache/           # content-addressed action cache
    └── fake-state.json  # fake-driver state (only used with --driver fake)
```

### `flow.yaml`

The single source of truth. Everything else is derived. See
[Flow schema](../reference/flow-schema.md).

### `generated.yaml` (materialized outputs)

Nodes with an `out:` field (e.g. `app-manifests`) can write their output
to a file. `afon render` runs those nodes and writes the file with a
provenance header:

```yaml
# Generated by afon render — do not edit (edit the flow instead)
```

Rules:

- `plan` and `apply` **read the file as-is**; they never re-render it
  implicitly.
- If you hand-edit the body, the next `render` **refuses to clobber** it —
  pass `--force` to take ownership again.
- `afon render --check` compares without writing (exit 1 when stale).
- The file is gitignored (`generated.yaml` in `.gitignore`).

### `.afon/` — local state

| Path | Written by | Purpose |
|---|---|---|
| `.afon/cache/*.json` | `plan` and `apply` | Content-addressed results of action nodes. Written **only after a node succeeds** — a crashed run leaves no entry, which is why the next run redoes the work. |
| `.afon/fake-state.json` | `apply --driver fake` | The fake cluster's object state. |

State directory resolution: `--state-dir` wins, otherwise the **directory
containing the flow file** — never the process working directory, so two
runs from different folders agree. See
[Concepts: Caching](../concepts/caching.md).

Deleting `.afon/` is always safe: everything in it is a cache.

## In-cluster objects (k8s driver)

### Target namespace

Declared as `spec.target.namespace` in the flow (or required by the k8s
driver). Rules:

- `apply` and `rollback` **auto-create** it if missing — created plain,
  with no labels added by Afon.
- `plan`, `validate`, `status`, `history` **never create** anything.
  `plan` against a missing namespace fails fast with
  `create it before applying`.
- An existing namespace is **never modified** (labels and annotations
  stay yours).

### Release records

Each apply writes one numbered record as a Secret in the target
namespace:

```
afon.release.<flow-name>.v<sequence>
```

Holds status (`pending` → `succeeded`/`failed`/`rolledback`), timestamps,
the manifests as they were applied, and an inventory of live objects.
`history`, `status`, and `rollback` read these. See
[Release record schema](../reference/release-record-schema.md).

### Build namespace (`afon-build`)

Used by `image-build` for its throwaway Job:

- Auto-created by the build runner if missing, **with Pod Security
  `baseline` labels** (`pod-security.kubernetes.io/{audit,enforce,warn}=baseline`).
- Your credentials Secrets live here **by name**: the flow's
  `registrySecret` / `gitSecret` fields reference them; Afon never reads
  their contents (they are mounted into the Job).
- Kaniko pushes from inside the cluster; the pushed tag is always the
  resolved git SHA.

### Objects your flow applies

Every applied object gets Afon ownership labels (flow + node). Pruning
and rollback use them: Afon only ever touches objects it owns — an object
owned by a different flow is refused, never adopted.

## Source repository layout (for orientation)

Not a contributor guide — just where things live:

```
cmd/afon/          CLI (cobra commands, flag wiring)
pkg/schema/        flow.yaml parsing, positions, ${...} extraction
pkg/graph/         DAG, topological sort, cycle detection
pkg/engine/        executor, cache, plan model, render, node registry
pkg/driver/        driver interfaces + fake and Kubernetes implementations
pkg/build/         pipeline nodes: git-source, image-build, Job runner
pkg/probe/         cluster profile probing (inspect)
pkg/release/       release record model + staleness rules
docs/              this documentation + design decisions + roadmap
examples/          placeholder-based example flows (all node types)
demo/              local demo flows (not part of the docs)
```
